## Met1
- POST /posts -> 201 Created, { "id": 101, ... }
- GET /posts/101 → 404 Not Found
- вывод: запись не сохранилась, песочница имитирует создание

## Met3
- Поля, которые послал: name
- Поля в ответе на PUT: name, id
- Поля в ответе на PATCH: id, name, username, email, address, phone, website, company
- Поля, которых не посылал, но они пришли (в PATCH): username, email, address, phone, website, company
- Вывод: слияние. PUT заменяет ресурс целиком — остальные поля стёрты;
  PATCH обновляет только присланные поля, остальные сохраняются

## Met4
- Статус DELETE: 200 тело DELETE: {} (пустой объект)
- Теория разрешает успеху DELETE: 200 или 204
- Статус GET /posts/3 после удаления: 200
- Хватает ли одного статуса для веры: нет
- Чего не хватает для веры: контрольного чтения — GET того же адреса.
- Без него 200 от DELETE не доказывает, что ресурс исчез

## Met5
- PUT, отправка 1: 200 OK, {"name":"Dup","id":1}
- PUT, отправка 2: 200 OK, {"name":"Dup","id":1}
- Ответы PUT совпали: да
- POST, отправка 1, id: 101
- POST, отправка 2, id: 101
- id совпали: да
- Вывод: PUT идемпотентен — повторная отправка одного тела не меняет состояние.
  POST в теории не идемпотентен (каждый раз новый ресурс), но песочница это скрывает,
  возвращая тот же id 101

## Met6
метод | безопасен? | идемпотентен? | обоснование

## Met7
/api/getUsers  действие в: в пути (getUsers)  номер ресурса: нет номера  верная пара: GET /users
/api?action=deleteUser&id=5  действие в: в query (action)  номер ресурса: в query (id=5)  верная пара: DELETE /users/5
/users/5/remove действие в:  в пути (remove)  номер ресурса: в пути (5)  верная пара:  DELETE /users/5 
/posts/delete-all действие в: в пути (delete-all) номер ресурса: нет номера  верная пара:  DELETE /posts
Вывод: во всех четырёх адресах действие записано в пути или в query.
По REST действие должно уходить в метод, а в адресе остаётся только
ресурс с его номером
